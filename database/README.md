# Локальная тестовая БД курсового проекта

`clinic_course_test.sql` получен из приложенного SQL и предназначен **только** для отдельной тестовой базы `clinic_course_test`. Он удаляет и создаёт таблицы, поэтому повторный запуск стирает все изменения в этой базе. Заглушки хэшей в исходном файле заменены на bcrypt-хэши тестового пароля `demo123` через `pgcrypto`.

В текущей локальной среде база `clinic_course_test` уже создана и заполнена. Desktop-клиент использует роль `clinic_preview` с правами чтения основных таблиц и правом записи только в `user_theme`; пароль хранится в игнорируемом файле `Clinic/db.local.json`, который копируется в каталог сборки. Другой разработчик может создать собственную строку подключения через переменную `CLINIC_DB_CONNECTION`. Пример формата: `Clinic/db.local.example.json`.

Тестовые входы Desktop-клиента:

| Роль | Логин |
| --- | --- |
| Пациент | `kirillov` |
| Регистратор | `petrova` |
| Врач | `sokolov` |
| Лаборант | `lebedeva` |
| Администратор | `admin` |

Пароль для всех: `demo123`. Это фиктивные учётные записи только для тестовой базы. Браузерная сборка не подключается к PostgreSQL и продолжает использовать отдельные демо-данные.

Светлая или тёмная тема Desktop-клиента хранится в `user_theme` по `account_id` и восстанавливается на другом компьютере при работе с той же базой. Таблица добавляется миграцией `2026-10-01_user_theme.sql`; она также включена в полный тестовый скрипт. Тема экрана входа остаётся локальной настройкой устройства. В браузерном демо выбор темы действует до перезагрузки страницы.

## Для разработчика API

DFD показывает потоки `account/role`, `patient`, `schedule/appointment`, `visit/referral/prescription`, `service/invoice`, `audit`. Приложенный SQL содержит 20 исходных таблиц и 5 ролей, включая лаборанта; `user_theme` добавляет 21-ю таблицу. Старый `MyDbContext` создан по другой схеме из 14 таблиц (`user_account`, `audit_log`, `rendered_service` и т. д.) и **не должен использоваться для запросов к этой тестовой БД без повторного scaffolding**. Текущий Desktop-клиент читает SQL напрямую через `Clinic/Data/ClinicDatabase.cs`, не изменяя маршруты `Clinic.API`.

В SQL нет функций или триггеров для автоматической записи аудита и проверки прав на уровне БД. Прямая связь Desktop-клиента с PostgreSQL сделана для локального тестирования по запросу; тестовая роль может менять предпочтение темы любого аккаунта, поскольку общий пароль БД не позволяет безопасно привязать запись к текущему пользователю. В рабочей системе сохранение темы и контроль `account_id` должны выполняться через API; для рабочей архитектуры нужно перенести аутентификацию и доступ к медицинским данным в API и ограничить результаты по пользователю на сервере.

Проверка структуры и данных: `psql -h 127.0.0.1 -U voodeex -d clinic_course_test -c "SELECT count(*) FROM account;"`. Не выполняйте `clinic_course_test.sql` в существующей рабочей базе.
